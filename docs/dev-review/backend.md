# Backend and execution review

Reviewed on 2026-09-12 against the HistoPilot-dev checkout. This review covers local HTTP security, project persistence, extraction and feature workers, development training scheduling, compute-job launch/resume/cancellation, and their service tests. It does not establish clinical suitability or validate the scientific quality of any trained model.

## Verdict

The backend has a strong local-first foundation: scientific inputs are frozen independently from mutable execution state, workers keep persistent output and logs, and many storage operations already defend against accidental aliases, interrupted writes, and conflicting mutations. The most consequential weaknesses found in this review were at asynchronous boundaries: losing a launch acknowledgement, failing between process creation and registration, and treating optional progress files as prerequisites for controlling a job. Those weaknesses are corrected in this branch.

This is a useful research workstation application with substantial existing integrity safeguards. It should not yet be described as exhaustively hardened against every worker, operating-system, filesystem, or hardware failure. In particular, live GPU execution, driver loss, full-disk conditions, host reboot, and real multi-process cancellation were not exercised during this review. Existing user projects and jobs were left untouched.

## Existing safeguards worth retaining

- **Local browser boundary:** `api/security.py` checks Host, Origin, Fetch Metadata, and a process-local session capability. It also applies no-store to API responses and frame/content-type protection headers. This is an intentional loopback service boundary, not a multi-user authentication system.
- **Scientific storage:** `storage/scientific.py` uses short SQLite transactions, publication journals, staged immutable artifacts, content identities, directory synchronization, and recovery validation. Existing tests cover conflicting writes, modified artifacts, aliased paths, interrupted publication, and corruption. These are more important than replacing storage simply for architectural novelty.
- **Lock discipline:** `storage/project_lock.py` uses process-held POSIX locks, keeps the lock inode in place, and rejects nonregular or multiply linked lock files. `storage/lifecycle.py` separates reversible visibility changes from scientific identity and uses its own guarded durable state.
- **Frozen execution:** Training/compute launch keeps a verified source archive and records runtime versions. Resume checks the original plan and package-version contract. Changes to source files or immutable scientific references are checked before compute and again before publishing results.
- **Resource scheduling:** Development training and generic compute share CPU/RAM/GPU reservations. Per-run subprocesses isolate CUDA and DataLoader state. The scheduler distinguishes ordinary out-of-memory failures from fatal device failures and halts further dispatch when its evidence indicates a device failure.
- **Output validation:** Feature packing validates its job identity, source feature identity, materialization receipt, and completed tensor validation. Extraction success additionally requires a matching validation report with full expected slide coverage. Process exit zero alone is not treated as sufficient scientific evidence.
- **Operational separation:** tmux worker sessions keep important jobs independent of the browser/control-service lifetime; the HTTP process does not import models into CUDA. This review did not start or restart the HistoPilot server.

## Residual risks and recommended follow-up

1. **Process-tree ownership deserves a coordinated follow-up.** Generic compute's `job_processes` scans isolated worker-session members using boot ID, process start time, process group, session, and user ownership. Training waits for direct fold leaders, and its lease pruning currently treats a dead leader as a stale lease; neither proves that every DataLoader descendant has exited. Simply reusing the compute scan in lease pruning would leave other training status/cancel/cleanup paths inconsistent and could retain a reservation for children the UI cannot reach. A safe change should update group identity, lease pruning, cancellation, status, and final release together, with real disposable process-tree tests covering a killed scheduler, a killed fold parent, ignored SIGTERM, PID reuse, unreadable process evidence, and reboot. The current changes close registration and cleanup-loop failures; they do not close this pre-existing descendant-ownership limitation.
2. **Use fail-closed process evidence consistently.** Lifecycle deletion has a stricter `_confirmed_live` check than the permissive `process_alive` helper used by some scheduling paths. A process disappearing is normal; unreadable `/proc` evidence is a different condition. A dedicated follow-up should exercise restrictive `/proc` mounts and permission failures so they cannot be confused with proof that a worker stopped.
3. **Consolidate mutable job schemas gradually.** Extraction and packing use `state` with values such as `starting` and `succeeded`; training and generic compute use `status` with `queued` and `completed`. UI adapters currently bridge these differences. Shared typed read models and a documented transition table would reduce future inconsistencies without rewriting established scientific records.
4. **Strengthen older extraction receipts without breaking saved jobs.** TRIDENT's standalone runner supports older Python environments and does not write the same complete job-identity envelope as packing. The validation report already binds successful coverage to a job. A versioned receipt migration should eventually bind all terminal states to their plan/job identity as well, while preserving compatibility with existing workers.
5. **Continue bounding polling work.** Diagnostic logs are tailed and progress is read from small metadata files, but list views iterate stored job records. Benchmark projects with thousands of jobs and large metadata manifests before choosing pagination, caching, or summary indexes. Preserve input-freshness checks when optimizing them.
6. **Exercise real durability failures separately.** Atomic replacement and fsync are necessary, but tests here did not emulate filesystem exhaustion, WSL shutdown, storage detachment, or power loss. Run deliberate failure drills on disposable projects with checkpoint/resume validation and durable logs.

## Verification

All tests added in this review use temporary projects, synthetic arrays, fake executors, or controlled failure injection. They do not launch a real training job or HistoPilot server.

- Targeted regressions for progress isolation, malformed authoritative JSON, and startup cleanup: **11 passed** before adding NaN/overflow cases.
- Targeted compute/training checks after final compatibility fixes, including NaN/overflow, idempotent replay, resume, cancellation, and acknowledgement recovery: **14 passed**.
- Managed-directory/lock suite including all new concurrency tests: **10 passed**.
- Packing acknowledgement regression after correcting its replay fixture: **1 passed**.
- Final progress-contract tests plus compute cancellation regressions: **27 passed**.
- Independent-review regressions for the session-inspection race and deeply nested JSON: **10 passed** (`pytest -q tests/test_compute_jobs.py tests/test_training_execution.py tests/test_worker_robustness.py -k 'acknowledgement or session_probe or deeply_nested'`).
- Complete compute-job and optional-telemetry test files after those final fixes: **40 passed** (`pytest -q tests/test_worker_robustness.py tests/test_compute_jobs.py`).
- Ruff check over every backend and test file changed by this review: **passed**.

The root review runs the final combined suite after all agents' edits are stable. Its final result supersedes these targeted counts. An intermediate broader run exposed a compatibility regression from adding an unnecessary `progress: null` to every training run; that was corrected so absent progress remains absent, while unreadable progress carries an explicit warning. That intermediate sandboxed run was stopped after it ceased making progress; the root review handles integration tests outside the sandbox because TestClient startup can hang inside it.

Independent review added two final corrections: launch-error recovery rereads authoritative state **after** the potentially blocking tmux probe, preserving workers that finish during inspection; metadata readers enforce a 64-level nesting limit with an iterative traversal and convert decoder recursion failures into structured errors. Regression cases publish a worker result from inside `executor.running()` and test nested JSON at depths 65, 1500, and 20000. This prevents valid-but-extremely-nested optional telemetry from failing later in FastAPI response serialization.
