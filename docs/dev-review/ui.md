# HistoPilot UI and workflow review

Reviewed on the `HistoPilot-dev` branch, 2026-09-12. This review covers the local project workflow, shared forms and dialogs, progress reporting, recovery actions, and the roadmap. The original HistoPilot server was neither started nor restarted for this work.

## Verdict

The existing interface has a sound research workflow: the roadmap explains dependencies; datasets, protocols and feature bundles are versioned; computation is separate from publishing predictors; later test cohorts are prepared independently; and cleanup explicitly preserves files and supports recovery. Those distinctions are more valuable than a broad visual redesign.

The largest UI weaknesses were inaccurate operational states and inconsistent validation. A page can appear understandable while still giving the wrong next action: an empty inference threshold could silently become zero, an unsupported aggregation setting could reach a dead end during inference, and partially loaded job lists could look complete. These are trust and workflow defects. The dev changes correct them while preserving the existing layout and familiar workflow.

This is a source, regression-test, and offline browser-fixture review. It is not a claim that all possible project histories, devices, large cohorts, or live training/evaluation paths have been exercised.

## Existing behavior worth preserving

- `Start` distinguishes source folders from project storage, labels optional inputs, exposes unavailable saved projects and connection retry, and focuses headings when changing views.
- The roadmap shows prerequisites, cached refresh warnings, synthetic-demo status, and completion evidence. Local stage editors remain available for reviewing retained work when new inputs are unavailable.
- Dataset import separates source inspection, column mapping and review. Patient ID fallback requires an explicit choice; previews and freeze readiness are invalidated when scientific inputs change.
- Shared selectors preserve an explicitly unavailable saved value rather than silently picking a different dataset or protocol.
- The freeze dialog uses Radix dialog semantics, retains the naming draft on errors, prevents dismissing an in-flight freeze, and explains fixed contents versus editable labels.
- Cleanup reviews exact record names and dependencies, requires acknowledgement, retains files, prevents confirming changed previews, and reuses an operation ID after an uncertain response. It also distinguishes whole-project visibility from child-record state.
- The folder picker binds selection to the currently loaded path, prevents choosing a stale directory while loading, and differentiates folders, tables and files. Source selection is distinct from import.
- Numeric entry already had a reusable strict parser, accessible labels and explicit errors; extending its use was preferable to adding another validation mechanism.
- The stylesheet includes focus-visible treatment, skip links, responsive layouts, scrollable tables and reduced-motion support. These are useful foundations; source inspection alone cannot establish complete keyboard or screen-reader usability.

## Remaining limitations and recommended next work

1. **Unsaved editor navigation:** Data, Protocol and Test-cohort editors retain unsaved changes in local React state. They show revision/dirty status and have explicit draft saves, but there is no consistent browser-unload or in-app navigation guard. Navigation can still discard unsaved input. A follow-up should establish a shared dirty-state contract, then test save/discard/stay behavior across every editor and project switch. Adding isolated warnings to a subset of routes would leave inconsistent behavior.
2. **Maintainability:** `LocalProtocol.tsx` exceeds 2,000 lines and `LocalDataset.tsx` exceeds 1,000. Extracting cohesive steps and moving request orchestration into narrowly scoped hooks would make review and state-transition testing easier. Such a refactor should preserve the scientific invalidation contracts and is larger than these targeted corrections.
3. **First-load cost:** The production build includes a large initial UI bundle. The current application imports many stages synchronously. Route-level code splitting deserves a separate measurement and regression pass, especially because existing SSR tests depend on immediate page rendering.
4. **Comprehensive accessibility and visual testing:** Offline controls and static markup can validate selected behaviors. Real user workflows still need keyboard-only navigation, dialog focus restoration, responsive review on narrow screens, and realistic long record names/large tables.
5. **Live end-to-end evidence:** No real project was imported or mutated, no training/evaluation workload was launched, and no HistoPilot service was started. A later validation session against a server started by the user should exercise draft save/reload, freeze, feature preparation, job cancellation/resume and evaluation with representative project data.

## Verification

Targeted Vitest runs passed for numeric entry, test-cohort settings, roadmap semantics, compute status controls, aggregate job state, packing warnings, training progress, protocol capability guidance and System capability reporting. TypeScript validation also passed. The root review runs the full frontend suite and production build after integration and records final test counts.

The reusable offline fixture is `web/verification/InferenceFixture.tsx`. It imports the production inference controls and `reportEditorValidity`, makes no API calls, and exposes accepted save counts and numeric settings. It supports browser checks for blank versus explicit zero, partial decimal/scientific notation, bounds, opening collapsed invalid fields, and visibly unsupported legacy aggregation. The root review records the actual offline browser outcomes separately; the fixture itself does not establish live server behavior.
